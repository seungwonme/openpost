Use a MacBook for development and a Mac mini for the one instance that owns real
schedules, webhooks, connected accounts, and provider writes. This keeps the
fast edit-and-test loop separate from the machine that must stay online.

Do not run both instances as active workers for the same workspace. Two workers
sharing the same provider accounts can publish a scheduled post or send an
automation reply twice.

## Recommended topology

```text
MacBook
  ├─ source checkout and feature branches
  ├─ isolated SQLite database and media
  ├─ test provider accounts only
  └─ local Docker Compose or development server

Mac mini
  ├─ one pinned OpenPost image
  ├─ one persistent database and media store
  ├─ HTTPS reverse proxy and public media URL
  └─ the only instance with production provider accounts
```

The MacBook checkout is the source of changes. The Mac mini is the runtime for
the reviewed revision. Keep the two data sets separate; never copy a production
database into a development environment unless you have a private, approved
backup and a clear reason to handle its account data.

## Develop on the MacBook

For a quick local installation, use a loopback-only binding and a versioned
image:

```yaml
services:
  openpost:
    image: ghcr.io/getopenpost/openpost:v7.35.1
    ports:
      - "127.0.0.1:18080:8080"
```

Set all local URLs to `http://127.0.0.1:18080` and keep local provider
credentials out of the production configuration. Verify the instance before
using it:

```sh
curl -fsS http://127.0.0.1:18080/api/v1/ready
```

The response must report `"status":"ready"` and `"database":"ok"`.

When developing from source, use the pinned repository toolchain described in
[Development setup](/development/setup). A source checkout and a published
image are different execution paths: changing source files does not change a
running published image until you build and tag a new image.

## Prepare the Mac mini

Before connecting a provider, choose the final public origin and configure a
reverse proxy. Set these values to the same HTTPS origin:

```dotenv
OPENPOST_APP_URL=https://openpost.example.com
OPENPOST_PUBLIC_URL=https://openpost.example.com
OPENPOST_MEDIA_URL=https://openpost.example.com/media
```

The proxy must forward `/api/v1/`, `/media/`, and ordinary app requests. Provider
OAuth callbacks and provider media fetches must reach the Mac mini from the
public internet. See [Reverse proxy](/self-hosting/reverse-proxy) for proxy
trust, callback URLs, and large video uploads.

Use a release tag or an image built from an exact reviewed commit. Do not use
`latest` for the first production install or for a migration you may need to
reproduce. Keep the image tag, source commit, Compose file, and environment
configuration together in the deployment record.

## Move an instance to the Mac mini

There are two supported cases.

### Case 1: Move an already-used instance

Use the built-in **Settings -> Instance -> Backup and restore** flow. The ZIP
contains the database and uploaded media, but it does not contain environment
variables or the encryption key.

1. Stop or pause production work on the source instance.
2. Download a backup and keep it private. It contains account tokens and
   session records.
3. Install the same OpenPost release on the Mac mini.
4. Copy the original `.env` values, especially
   `OPENPOST_ENCRYPTION_KEY` and `OPENPOST_JWT_SECRET`, through a secret store.
5. Restore the ZIP on the Mac mini and confirm the restore only after checking
   the target paths and release.
6. Start the Mac mini instance and check `/api/v1/ready` and the logs.
7. Open a saved post with media and inspect one scheduled post before enabling
   provider work.
8. Update OAuth callback URLs in provider consoles if the public origin changed.
9. Keep the source instance stopped or disconnected from production accounts.

A restore with a different encryption key is refused because saved provider
credentials cannot be decrypted. Reconnect a provider only when its external
application or token was revoked during the move.

### Case 2: Start production after local development

Do not copy the MacBook's test database unless it is intentionally the source of
the new instance. Start the Mac mini with an empty persistent store, create the
first administrator, configure the public URLs, and connect the production
accounts there. This is the safer default for a new installation.

## Build and deliver a code change

Merge source changes into `main` first. The Mac mini then builds that exact
commit itself and runs it; nothing is run on the MacBook and no registry is
involved. `scripts/fork/macmini-deploy.sh` does every step and refuses commits
that are not on `origin/main`:

```sh
ssh macmini '/Users/aiden/Dev/2-area/nomadamas/12-playground/openpost/scripts/fork/macmini-deploy.sh --build'
```

`--build` builds the frontend and the `deploy/docker/Dockerfile` image as
`local/openpost:fork-<commit>` while the old container keeps serving. It then
stops OpenPost, archives the data volume with `.env` and both Compose files,
restores that archive into a scratch volume to check the database, and starts
the new image. It reports readiness, the running version, the newest applied
migration, and whether the main row counts changed.

To run a published upstream release instead, pin it by digest:

```sh
scripts/fork/macmini-deploy.sh --image ghcr.io/getopenpost/openpost:v7.37.1@sha256:<digest>
```

The combined `all` container applies database migrations at startup, so roll
back the data and the image together. Each backup records the image that was
running:

```sh
scripts/fork/macmini-deploy.sh --restore ~/Backups/openpost/<timestamp>
```

Copy each backup off the Mac mini after a deployment:

```sh
rsync -a macmini:Backups/openpost/<timestamp>/ ~/Backups/openpost/<timestamp>/
```

## Operational boundaries

- Keep the Mac mini's OpenPost port private behind the reverse proxy.
- Use one production worker for each database and workspace set.
- Back up the database, media, Compose file, image tag, and secrets together.
- Keep `OPENPOST_ENCRYPTION_KEY` stable across restarts and restores.
- Check `/api/v1/ready` after every restart and after every migration.
- Test a saved post, a media asset, and a scheduled post after a restore.
- Do not enable OAuth until the public HTTPS and media URL work from outside
  the local network.
- Do not treat a successful OAuth callback as proof that video publishing,
  comments, analytics, or direct messages are enabled.

For the full backup, upgrade, and recovery procedure, see [Maintenance](/self-hosting/maintenance).

## Mac mini runtime cutover

The production OpenPost runtime for this fork runs on the Mac mini. Develop over SSH in the Mac mini checkout and verify the public application through `https://openpost.aidenahn.com`.

```text
SSH -> /Users/aiden/Dev/2-area/nomadamas/12-playground/openpost
     -> Docker Compose OpenPost (127.0.0.1:18081)
     -> aiden-edge Docker network
     -> Caddy gateway
     -> macmini-services Cloudflare Tunnel
     -> https://openpost.aidenahn.com
```

The MacBook instance is stopped. Do not run a second worker against the same workspace or provider accounts.

### Mac mini deployment files

- OpenPost checkout: `/Users/aiden/Dev/2-area/nomadamas/12-playground/openpost`
- Branch: `main` (`--build` fast-forwards it to `origin/main`)
- Base Compose file: `docker-compose.yml` (the portable default for ordinary local users)
- Mac mini deployment file: `docker-compose.macmini.yml` (the Mac mini-specific override; pins the Compose project `openpost`)
- Persistent volume: `openpost_openpost_data` (external and named explicitly, so moving the checkout keeps the data)
- Runtime image: `DEPLOY_IMAGE` in the private `.env`, written by `scripts/fork/macmini-deploy.sh`
- Backups: `/Users/aiden/Backups/openpost/<timestamp>/`, one per deployment
- OpenPost host port: `127.0.0.1:18081`
- Shared network: `aiden-edge`
- Ingress checkout: `/Users/aiden/Dev/agent-portability`
- Ingress tunnel: `macmini-services`

The base Compose file remains portable for ordinary local users. On the Mac
mini, always layer the Mac mini deployment file over it so the recorded image,
private host binding, shared ingress network, and named volume are applied
together. The deploy script also writes `COMPOSE_FILE` to `.env`, so a plain
`docker compose` in the checkout uses both files, and the overlay refuses to
start without `DEPLOY_IMAGE`:

```sh
docker compose config
```

The commands below assume the Mac mini checkout has its private `.env` file.
Run them from that checkout; the base file's `env_file` entry is intentionally
not copied into the repository's public documentation.

Keep `.env` private. It contains the stable `OPENPOST_ENCRYPTION_KEY` and `OPENPOST_JWT_SECRET`, and must not be committed or copied into GitHub issues.

### Develop and verify

Building the frontend or backend in the checkout does not change the running
container, which always runs an image. Deploy a merged change with
`--build` as described above, then check the public URL:

```sh
ssh macmini '/Users/aiden/Dev/2-area/nomadamas/12-playground/openpost/scripts/fork/macmini-deploy.sh --status'
curl -fsS https://openpost.aidenahn.com/api/v1/ready
```

The public URL is the test surface. OAuth callbacks and provider media URLs continue to use `openpost.aidenahn.com`; do not rename the hostname without re-registering every provider callback.

To restart the Mac mini service without changing its image or configuration,
use the same overlay and check readiness again:

```sh
docker compose restart openpost
curl -fsS http://127.0.0.1:18081/api/v1/ready
```

### Ingress update

The shared Caddy and Cloudflare configuration owns the public route:

- `infra/ingress/Caddyfile`: `openpost.aidenahn.com` proxies to `openpost:8080`.
- `infra/ingress/cloudflared.yml`: `openpost.aidenahn.com` routes to the shared gateway.

After changing those files, validate and restart the shared ingress from `/Users/aiden/Dev/agent-portability`:

```sh
./ops check ingress
./ops restart ingress
./ops status ingress
```

### Backup before upgrades

Stop provider work before a migration. Back up the persistent volume and retain the exact image tag, Compose file, and secret version together. The database and media contain provider tokens and must remain private.

```sh
mkdir -p /tmp/openpost-backup

docker compose -f docker-compose.yml -f docker-compose.macmini.yml stop openpost

docker run --rm \
  -v openpost_openpost_data:/data \
  -v /tmp/openpost-backup:/backup \
  alpine:3.20 \
  sh -c 'tar czf /backup/openpost-data.tgz -C /data .'

sha256sum /tmp/openpost-backup/openpost-data.tgz
```

To roll back, stop OpenPost with the same Compose overlay, restore the matching
volume backup, run the matching immutable image with the overlay, and verify
`/api/v1/ready` before enabling provider work. Never roll back a binary across a
schema migration without the corresponding database restore.
